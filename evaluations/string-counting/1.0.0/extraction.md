# Legacy extraction policy 1.0.0 (verifier-only)

Status: specified, not implemented. Input is the frozen final Answer, never Reasoning. Hash the original result bytes and UTF-8 encoding of the decoded Answer; offsets below refer to that UTF-8 Answer. Never edit original artifacts.

1. Empty/whitespace-only Answer: submission fail, reason `missingSubmission`; downstream checks notRun. Do not turn absent code into an empty method.
2. Exactly one well-formed Markdown fenced payload explicitly labeled `csharp` or `cs`, with no other code-bearing region: the complete payload may be the submission. Record fence and payload byte ranges; preserve payload bytes including whitespace, duplicate declarations and examples. Fence delimiters are framing only. If material outside the payload might contain code or required example content, classification is ambiguous; do not discard it.
3. An entirely code-only Answer may be retained in full after a reviewer records that classification. No trimming, newline normalization or comment removal. This review is a projection decision, not a correctness verdict.
4. Multiple fenced payloads, unmatched fences, code/prose mixtures without one clear submission, multiple possible method bindings, or uncertainty about example separation: submission notRun with `ambiguousSubmission`; downstream checks notRun. Record why and what clarification is needed. This is an abstention/coverage limitation, not candidate fail or evaluator error. Never select a better-looking method, concatenate competing alternatives or select the first successful compiler input.
5. Repeated declarations inside one unambiguous payload are preserved; when an isolated compiler exists, that input fails compilation if the declarations conflict. Do not deduplicate or reinterpret a duplicate as an alternative answer. Multiple blocks remain ambiguous under rule 4 regardless of apparent quality.
6. A candidate that is clearly code but lacks a compatible method is a submission failure (`missingMethod`), not an opportunity to synthesize one. If binding is uncertain, abstain under rule 4. Usage-example presence is a separate required review/check; no execution of example code is necessary to establish its presence.

A future extraction artifact must record: policy ID/version/hash; source result and Answer hashes; classification and reason; all retained/excluded byte ranges and rationale; reviewer identity/reference for human decisions; unique method binding if resolved; output candidate hash; and every trusted wrapper/import added. No formatter, repair, renaming, null guard, trimming, deduplication, declaration deletion or signature change is allowed. Candidate body bytes remain intact. Any namespace/class/import wrapper needed to compile a standalone method must be separately stored and hash-bound, justified as mechanical scaffolding, and approved in the verifier version. No such wrapper is implemented in 1B.1.

Unresolved decisions must not be silently converted to pass/fail. Reclassification later produces a new evaluation artifact with its review provenance; it never overwrites earlier evidence. The legacy policy's abstentions must be shown in coverage and denominator reporting, and must not be mixed with strict-format benchmark results.
