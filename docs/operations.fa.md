# ⁧راهنمای عملیاتی LocalModelLab — فاز 1A⁩

⁧نسخه سخت‌سازی harness برابر `1.1.0` است. توضیح ترتیب اجرای زیر برای پروفایل‌های قدیمی با `modelFirst` و `providerManaged` برقرار است. برای مقایسه چهار مدل، فایل `benchmarks/comparison.v1.json` و [دستورهای مقایسه کنترل‌شده](comparison.md) را استفاده کنید.⁩

⁧در سیاست `rotating`، ابتدا دورهای warmup و سپس دورهای اندازه‌گیری اجرا می‌شوند. در هر دور و هر مورد، نقطه شروع فهرست مدل‌ها چرخش می‌کند؛ ترتیب دقیق پیش از استنتاج در `schedule.json` ذخیره می‌شود. چهار تکرار برای چهار مدل جایگاه‌ها را متوازن می‌کند، اما اثر دما و کش را حذف نمی‌کند.⁩

⁧سیاست `singleModel` مدل‌های مقیم دیگر را، حتی اگر جزو مدل‌های انتخاب‌شده نباشند، با درخواست تخلیه خارج می‌کند و وضعیت `api/ps` را پیش و پس از استنتاج بررسی می‌کند. از سرویس اختصاصی استفاده کنید. شکست بررسی اقامت، تلاش را ناموفق می‌کند؛ این سیاست زمان بارگذاری را حذف نمی‌کند و اجرای گرم را تضمین نمی‌کند. در سیاست پیش‌فرض `providerManaged` مدیریت حافظه همچنان با ارائه‌دهنده است.⁩

⁧پس از ایجاد پوشه اجرا، شکست پیش‌بررسی در `state.json` با `phase` و `failureKind` ثبت می‌شود. نوع خطا میان `invalidConfiguration`، `unavailableModel`، `providerFailure` و `cancelled` تفاوت می‌گذارد. تعریف و انتخاب‌ها حفظ می‌شوند؛ ممکن است `manifest.json` هنوز وجود نداشته باشد. دستورهای inspect و report این حالت را پشتیبانی می‌کنند. خطای خواندن یا ساختار فایل ورودی و گزینه‌های خط فرمان می‌تواند پیش از ایجاد پوشه رخ دهد.⁩

⁧مشخصات سخت‌افزار داده ثابت است و نمونه زمان‌دار `api/ps` فقط وضعیت اقامت را نشان می‌دهد. مصرف CPU و GPU، بیشینه VRAM و انرژی اندازه‌گیری نشده‌اند؛ نسبت دقیق اجرای CPU/GPU از این داده‌ها استنتاج نمی‌شود. مهلت تلاش اکنون آماده‌سازی اقامت و بررسی‌های پس از پاسخ را نیز محدود می‌کند؛ `clientElapsedMs` همچنان فقط بازه درخواست استنتاج است.⁩

⁧این ابزار پاسخ مدل و عملکرد استنتاج را جمع‌آوری می‌کند. کد تولیدشده اجرا یا کامپایل نمی‌شود و برای درستی پاسخ، کیفیت کد یا رتبه‌بندی عمومی مدل‌ها امتیازی وجود ندارد.⁩

## ⁧نصب و بررسی اولیه⁩

⁧روی ویندوز به یک SDK دات‌نت با پشتیبانی از net8.0، محیط اجرای .NET 8 و سرویس Ollama نیاز دارید. دستورات را از ریشه مخزن اجرا کنید. ابزار مدل دانلود نمی‌کند؛ نام دقیق مدل نصب‌شده را از خروجی دستور زیر بردارید. اجرای تست‌ها به Ollama نیاز ندارد.⁩

```powershell
dotnet build LocalModelLab.sln -c Release
dotnet test LocalModelLab.sln -c Release
dotnet run --project LocalModelLab.Cli -c Release -- models list
dotnet run --project LocalModelLab.Cli -c Release -- cases validate
```

⁧خروجی فهرست مدل‌ها شامل digest، اندازه، جزئیات مدل، داده‌های show و قابلیت‌هاست. آدرس پیش‌فرض سرویس http://localhost:11434/ است؛ برای تغییر آن از گزینه زیر استفاده کنید. آدرس و مشخصات ماشین در artifact ذخیره می‌شوند.⁩

```powershell
dotnet run --project LocalModelLab.Cli -c Release -- models list --endpoint http://localhost:11434/
```

## ⁧اجرای کوتاه و اجرای اصلی⁩

⁧برای بررسی اتصال، مجموعه و پروفایل smoke یک مورد را با یک warmup و یک تلاش اندازه‌گیری‌شده اجرا می‌کنند. محدودیت خروجی 64 توکن است؛ در نتیجه کوتاه‌شدن پاسخ طبیعی است و در نتیجه ثبت می‌شود.⁩

```powershell
dotnet run --project LocalModelLab.Cli -c Release -- benchmark run --models granite4:3b --suite smoke --profile smoke
```

⁧برای اجرای چهار مورد اولیه از تنظیمات پیش‌فرض استفاده کنید. هر مورد یک warmup و سه تکرار اندازه‌گیری‌شده دارد. مدل‌ها، موارد و تکرارها به ترتیب تعریف‌شده و به صورت ترتیبی اجرا می‌شوند. هر تلاش فقط پیام‌های system و user همان مورد را می‌فرستد؛ پاسخ تلاش قبلی به تاریخچه اضافه نمی‌شود. کش داخلی و اقامت مدل در حافظه به وسیله ارائه‌دهنده مدیریت می‌شوند و با استقلال مکالمه تفاوت دارند.⁩

```powershell
dotnet run --project LocalModelLab.Cli -c Release -- benchmark run --models granite4:3b
dotnet run --project LocalModelLab.Cli -c Release -- benchmark run --models "granite4:3b,qwen2.5-coder:7b" --suite initial --profile default --output results
```

⁧اجرای هم‌زمان پیاده‌سازی نشده است. روی سخت‌افزار دارای 16 گیگابایت RAM و 6 گیگابایت VRAM ابتدا اجرای کوتاه را بررسی کنید؛ جاگیری مدل، کش و بار سایر برنامه‌ها بر زمان و مصرف حافظه اثر دارند. هیچ مدل یا تنظیمی به صورت خودکار جایگزین نمی‌شود.⁩

## ⁧تعریف موارد، مجموعه‌ها و پروفایل‌ها⁩

⁧فایل benchmarks/initial.v1.json دارای schemaVersion برابر 1 و سه بخش cases، suites و profiles است. هر عضو id و version مستقل دارد. مورد شامل prompt و system اختیاری است؛ مجموعه ترتیب شناسه موارد را تعیین می‌کند. چهار مورد اولیه توضیح کد سی‌شارپ، تشخیص باگ، تولید کد و توضیح فنی فارسی هستند.⁩

⁧برای تغییر یک بنچمارک، یک نسخه جدید از فایل بسازید و version عضوهای تغییرکرده را افزایش دهید. فایل قدیمی و پوشه اجرای قبلی را ویرایش نکنید. SHA-256 کل بایت‌های فایل و fingerprint ساختاری هر مورد، مجموعه و پروفایل ثبت می‌شود؛ بنابراین حتی تغییر بدون افزایش نسخه نیز قابل تشخیص است. فیلد ناشناخته، شناسه تکراری، ارجاع نامعتبر و تنظیمات عددی نامعتبر خطا هستند.⁩

```powershell
dotnet run --project LocalModelLab.Cli -c Release -- cases validate --definitions benchmarks/custom.v2.json
dotnet run --project LocalModelLab.Cli -c Release -- benchmark run --models granite4:3b --definitions benchmarks/custom.v2.json --suite initial --profile default
```

⁧در پروفایل، warmups و repetitions تعداد تلاش‌ها، temperature دما در بازه 0 تا 2، seed بذر، numCtx طول زمینه، numPredict سقف خروجی، stream نوع دریافت، timeoutSeconds مهلت کل درخواست و keepAliveSeconds مدت نگهداری مدل در حافظه پس از درخواست را تعیین می‌کنند. مقادیر پیش‌فرض پروفایل نمونه به ترتیب 1، 3، 0، 42، 4096، 512، true، 180 و 300 هستند. مقدار صفر برای keepAliveSeconds درخواست تخلیه مدل پس از پاسخ است. timeoutSeconds و keepAliveSeconds حداکثر 86400 هستند. سقف هر اجرا 999999 تلاش است.⁩

⁧seed تکرارپذیری بیت‌به‌بیت را تضمین نمی‌کند؛ نسخه ارائه‌دهنده، سخت‌افزار و پیاده‌سازی مدل نیز مؤثرند. مقدارهای ارسالی دقیقاً ذخیره می‌شوند؛ اگر Ollama مقدار مؤثر داخلی را گزارش نکند، ابزار ادعا نمی‌کند که آن را تأیید کرده است. پارامترهای پیش‌فرض و template مدل نیز در داده show نگهداری می‌شوند. پس از هر پاسخ، داده api/ps خارج از بازه زمان‌گیری خوانده می‌شود؛ context_length مؤثر در صورت وجود با numCtx مقایسه می‌شود و تفاوت آن خطای صریح است. نبود داده runtime در runtimeMetadataError ثبت می‌شود و مقدار مشاهده‌نشده null می‌ماند.⁩

## ⁧قابلیت‌ها و حالت تفکر⁩

⁧وضعیت supported پشتیبانی تأییدشده، unsupported نبود پشتیبانی، unknown نامعلوم‌بودن و missing نبود داده قابلیت است. برای اجرا، Chat باید supported باشد. مدل embedding یا مدل ابری در این فاز اجرا نمی‌شود. قابلیت‌های Chat، FIM، Embedding، Vision، Decision و Thinking از هم جدا هستند؛ در این فاز فقط Chat اجرا می‌شود.⁩

⁧برای کنترل تفکر، فیلد thinking را به پروفایل اضافه کنید؛ مقدار می‌تواند true، false یا یک رشته دقیقاً مطابق مقادیر اعلام‌شده مدل باشد. حذف این فیلد یعنی استفاده از پیش‌فرض مدل. رشته‌ای مانند off جایگزین خودکار false نمی‌شود. درخواست خام Ollama از کلید think استفاده می‌کند.⁩

⁧اگر نسخه Ollama مقادیر معتبر تفکر را اعلام نکند، اجرای دارای thinking صریح متوقف می‌شود. فقط در صورت داشتن اطلاعات معتبر، بخش modelDeclarations را با نام دقیق مدل، digest واقعی و مقادیر تأییدشده اضافه کنید. این داده به همان digest محدود است و نمی‌تواند با قابلیت قطعی ارائه‌دهنده تناقض داشته باشد. مثال زیر الگو است و تا جایگزینی digest قابل استفاده نیست.⁩

```json
"modelDeclarations": [
  {
    "model": "example:tag",
    "digest": "REPLACE_WITH_EXACT_DIGEST",
    "capabilities": { "chat": "supported", "thinking": "supported" },
    "thinkingValues": [true, false]
  }
]
```

⁧همه مدل‌های انتخاب‌شده پیش از اولین استنتاج اعتبارسنجی می‌شوند. خطای HTTP، گزینه نامعتبر، قطع stream یا کمبود حافظه به تلاش جدید یا تغییر تنظیمات منجر نمی‌شود. تکرارهای بعدی برنامه‌ریزی‌شده مستقل هستند و در صورت خطای یک تلاش همچنان اجرا می‌شوند؛ این رفتار retry نیست. تغییر digest اجرای ادامه کار با آن مدل را متوقف می‌کند.⁩

## ⁧artifact و توقف اجرا⁩

⁧ابتدای اجرا مسیر پوشه یکتا چاپ می‌شود. manifest.json شامل نسخه harness، hash اسمبلی‌ها، نسخه ارائه‌دهنده، endpoint، مشخصات ماشین، snapshot مدل‌ها و تعریف انتخاب‌شده است. definitions.json بایت‌های فایل ورودی را حفظ می‌کند. state.json وضعیت اجرا و تعداد تلاش‌های نهایی‌شده را نگه می‌دارد.⁩

```text
results/RUN_ID/
  manifest.json
  definitions.json
  state.json
  attempts/000001/
    request.json
    response.raw
    result.json
  reports/REPORT_ID/
    report.md
    attempts.csv
    summary.csv
```

⁧درخواست قبل از ارسال ذخیره می‌شود. response.raw بایت‌های بدنه HTTP دریافتی است و پیش از تبدیل به متن روی دیسک نوشته می‌شود؛ headerهای پاسخ در نتیجه ثبت می‌شوند. این فایل ضبط بسته‌های شبکه یا قالب wire در HTTP نیست. در پاسخ‌های جریانی، reasoning فقط وقتی فیلد مجزای thinking وجود داشته باشد جدا می‌شود؛ ابزار از روی تگ‌های متن حدس نمی‌زند. نبود این داده null باقی می‌ماند.⁩

⁧با Ctrl+C، تلاش فعال با وضعیت interrupted نهایی و تلاش‌های بعدی متوقف می‌شوند. وضعیت timedOut برای پایان مهلت و failed برای خطای درخواست یا پردازش است. هر JSON با نوشتن فایل موقت، flush و جابه‌جایی اتمی همان فایل ثبت می‌شود. تراکنش چندفایلی یا تضمین در برابر خرابی دیسک وجود ندارد.⁩

⁧اگر فرایند به اجبار بسته شود، داده خام دریافت‌شده و آخرین JSON معتبر حفظ می‌شوند؛ ممکن است state همچنان running و تلاش inProgress باشد. دستور inspect این وضعیت را نشان می‌دهد و report داده موجود را می‌خواند. ادامه همان اجرا پیاده‌سازی نشده؛ اجرای بعدی پوشه جدید می‌سازد. پوشه‌های نتیجه اطلاعات prompt، پاسخ و مشخصات میزبان دارند و به صورت پیش‌فرض در Git نادیده گرفته می‌شوند.⁩

## ⁧گزارش و تفسیر اندازه‌گیری‌ها⁩

```powershell
dotnet run --project LocalModelLab.Cli -c Release -- benchmark inspect --run "results/RUN_ID"
dotnet run --project LocalModelLab.Cli -c Release -- benchmark inspect --run "results/RUN_ID" --attempt 000002
dotnet run --project LocalModelLab.Cli -c Release -- benchmark report --run "results/RUN_ID"
```

⁧هر بار ساخت گزارش، یک پوشه تازه ایجاد می‌شود. گزارش Markdown و summary.csv برای هر مدل و هر زوج مدل/مورد، تعداد موفق، خطا، تلاش ناتمام، کوتاه‌شدن خروجی و میانگین زمان‌ها را نشان می‌دهند. attempts.csv جزئیات همه تلاش‌ها، از جمله warmupها را دارد. میانگین‌ها فقط از تلاش‌های measured با وضعیت completed و مقدار موجود ساخته می‌شوند؛ پاسخ دارای پایان length همچنان completed است و جداگانه کوتاه‌شده شمرده می‌شود.⁩

⁧clientElapsedMs با ساعت monotonic اندازه‌گیری می‌شود و ارسال، دریافت و ثبت جریانی روی دیسک را در بر می‌گیرد. زمان اولین خروجی، پاسخ و reasoning از آغاز درخواست تا مشاهده متن غیرخالی است؛ این اندازه‌گیری زمان دقیق اولین توکن داخل موتور نیست. برای پاسخ غیرجریانی این زمان‌ها null هستند.⁩

⁧داده‌های total_duration، load_duration، prompt_eval_duration و eval_duration ارائه‌دهنده بر حسب نانوثانیه جدا نگهداری می‌شوند. زمان ارائه‌دهنده منهای بارگذاری فقط در صورت وجود هر دو عدد محاسبه می‌شود و تضمین اجرای گرم نیست. حتی بعد از warmup ممکن است مدل از حافظه خارج شده باشد؛ همیشه loadNs همان تلاش را بررسی کنید.⁩

⁧نرخ تولید از eval_count و eval_duration محاسبه می‌شود و ممکن است توکن‌های reasoning را هم شامل شود. ابزار تعداد توکن پاسخ و تفکر را حدس نمی‌زند. نرخ مدل‌ها با tokenizerهای متفاوت معیار مستقیم برتری نیست. null یعنی اندازه‌گیری موجود نیست، نه صفر.⁩

⁧completionReason دقیقاً حفظ می‌شود. دلیل length یعنی خروجی کوتاه شده، stop یعنی پایان عادی، و دلیل ناشناخته یا غایب یعنی وضعیت کوتاه‌شدن نامعلوم است. قطع stream بدون done نیز خطا و خروجی ناقص است. هیچ امتیاز درستی یا ارزیابی خوداظهاری مدل در گزارش وجود ندارد.⁩

⁧کد خروج 0 موفقیت، 1 خطای اعتبارسنجی یا وجود تلاش ناموفق و 130 توقف کاربر است. پیش از مقایسه اجراها، hash مدل، موارد، پروفایل و harness و نیز نسخه Ollama و وضعیت سخت‌افزار را بررسی کنید. در طول اجرا مدل‌ها را حذف یا به‌روزرسانی نکنید؛ بررسی digest پیش و پس از تلاش احتمال تغییر را تشخیص می‌دهد اما جای قفل روی مدل خارجی را نمی‌گیرد.⁩

## ⁧محدودیت و ادامه کار⁩

⁧در این فاز اجرای موازی، resume، اجرای FIM یا embedding، ابزار و agent، RAG، داشبورد و داوری LLM وجود ندارد. ظرفیت VRAM در صورت دسترسی از خروجی nvidia-smi با واحد MiB ثبت می‌شود. داده Win32_VideoController به تنهایی برای ظرفیت دقیق قابل اتکا نیست و با توضیح محدودیت حفظ می‌شود. تنظیمات مؤثر داخلی که Ollama اعلام نمی‌کند نامعلوم باقی می‌مانند.⁩

⁧فاز 1B نیازمند تأیید جداگانه برای قراردادهای ارزیابی مستقل، checks قطعی، سیاست منابع و ایزوله‌سازی است. هر اجرای احتمالی کد باید پس از طراحی مرز امنیتی worker انجام شود؛ اندازه‌گیری استنتاج همچنان از نتایج ارزیابی جدا خواهد ماند.⁩
